# Step 2 — 수집 항목 인벤토리 만들기

**이 표가 이후 모든 점검의 기준선이다.** 방침 점검도, 초안 작성도 여기서 나온다.

## 원칙

- **실제로 확인한 것만 적는다.** 추측하지 않는다. "아마 이메일도 받을 것이다"는 쓰지 않는다.
- 확인 못 한 항목은 표에서 빼지 말고 `확인 필요` 상태로 남긴다. 빠뜨리면 없는 것처럼 보인다.
- 각 행에 **근거**를 남긴다 (파일:줄 번호, 또는 확인한 화면 URL). 나중에 대조할 때 필요하다.

## 인벤토리 표 형식

| 수집 정보 | 수집 시점·위치 | 저장 위치 | 동의 절차 | 외부 전송 | 삭제 가능 | 근거 |
|---|---|---|---|---|---|---|
| 이메일 | 회원가입 폼 | `users.email` (Supabase) | 가입 시 체크박스 있음 | 없음 | 탈퇴 시 soft delete만 ⚠️ | `app/signup/page.tsx:42` |
| 프로필 이미지 URL | 구글 소셜 로그인 | `users.avatar_url` | 별도 고지 없음 ⚠️ | Google | 미확인 | `lib/auth.ts:18` |
| IP·User-Agent | 모든 요청 | Vercel 로그 (미국) | 없음 | Vercel | 불가 | 자동 수집 |

표 아래에 반드시 두 블록을 덧붙인다.

### ⚠️ 사용자가 예상 못 할 만한 수집 항목

내가 의도해서 넣지 않았는데 수집되고 있는 것들. 여기가 대부분의 문제가 나오는 자리다.

### ❓ 확인 필요

접근 권한이 없거나 코드에서 판단이 안 서는 항목. 무엇을 어떻게 확인하면 되는지까지 적는다.

---

## 모드 A — 코드 저장소에서 파악

`Grep`과 `Glob`으로 훑고, 의심 지점만 `Read`한다. 전체 파일을 다 읽지 않는다.

### 1) 입력을 받는 지점

폼, API 라우트, 서버 액션에서 사용자 입력을 받는 곳을 찾는다.

```
- 폼 필드:      <input, <textarea, name=, register(, formData.get(
- API 핸들러:   route.ts, api/, app.post(, @PostMapping, def post(
- 스키마 검증:  zod, yup, joi, pydantic — 여기 정의된 필드가 곧 수집 항목이다
```

**스키마 정의 파일이 있으면 그게 가장 정확한 목록이다.** 먼저 찾는다.

### 2) 저장 위치

```
- 마이그레이션·스키마: schema.prisma, migrations/, *.sql, models.py
- ORM 모델 정의
- 파일 업로드 경로, S3·Storage 버킷 설정
- 로컬 저장: localStorage, sessionStorage, 쿠키 설정 코드
```

컬럼 이름만 봐도 개인정보 여부가 대체로 드러난다: `email`, `phone`, `name`, `address`, `birth`, `gender`, `ip`, `device_id`, `avatar`.

### 3) 동의를 받는 절차

```
- 가입·문의 폼 근처의 체크박스: agree, consent, terms, privacy, 동의
- 체크박스가 required인가, 기본 체크되어 있는가 (기본 체크는 문제다)
- 필수 동의와 선택 동의가 분리되어 있는가
- 동의한 사실을 저장하는가 (consent 관련 컬럼·테이블)
```

동의 기록을 저장하지 않으면 나중에 "동의받았다"를 입증할 수 없다. 이것도 지적 항목이다.

### 4) 외부로 나가는 정보 — 가장 많이 놓치는 곳

```
- package.json / requirements.txt / go.mod 의존성 목록
- 환경변수 이름 (.env.example, 배포 설정)
- fetch·axios·httpx 호출 대상 도메인
```

유형별로 확인한다:

| 유형 | 흔한 예 | 확인할 것 |
|---|---|---|
| 인증 | Google·Kakao·Naver·Apple OAuth, Clerk, Auth0 | 어떤 스코프를 요청하는가 |
| 분석 | GA, Amplitude, Mixpanel, Hotjar, Clarity | 사용자 식별자를 보내는가, 세션 녹화가 켜져 있는가 |
| 에러 추적 | Sentry, Datadog | 요청 본문·사용자 정보가 함께 전송되는가 |
| 결제 | Stripe, 토스페이먼츠, 아임포트 | 카드 정보를 직접 저장하는가 (직접 저장이면 별도 기준) |
| 알림 | SendGrid, Resend, Twilio, 알리고, 카카오 알림톡 | 마케팅 발송에도 쓰이는가 → Step 5로 연결 |
| **AI API** | OpenAI, Anthropic, Gemini | **사용자 입력이 그대로 나가는가, 학습에 쓰이는가** |
| 인프라 | Vercel, Supabase, Firebase, AWS | **리전이 국외인가** → 해외 경고 트리거 |

**AI API와 인프라 리전은 반드시 확인한다.** 2026년 개정 처리방침 작성지침에 생성형 AI 서비스 부록이 신설되어, AI 처리 관련 사항을 방침에 기재하도록 안내하고 있다. 그리고 국외 저장은 국외 이전 고지 대상이다.

### 5) 지우는 기능 — 말과 실제가 갈리는 지점

```
- 탈퇴 엔드포인트: delete, withdraw, deactivate, /account
- 실제 동작: DELETE 쿼리인가, deleted_at 플래그인가
- 연관 데이터: 게시글·업로드 파일·로그는 같이 지워지는가
- 백업·외부 서비스에 남은 데이터는 어떻게 되는가
```

**`deleted_at` 플래그만 세우고 있다면, 방침에 "파기한다"고 적혀 있는지 반드시 확인한다.** 여기가 이 점검에서 가장 자주 나오는 🔴 항목이다.

## 모드 B — 배포된 URL에서 파악

브라우저 도구로 실제 화면을 확인한다. 코드로는 안 보이는 것들이 여기서 드러난다.

**확인 순서:**

1. **방침 페이지 찾기** — 푸터 링크, `/privacy`, `/privacy-policy`, `/개인정보처리방침` 시도
   - 링크가 살아 있는가 (404 아닌가)
   - **로그인 없이 볼 수 있는가** (가입 전에 읽을 수 있어야 한다)
   - 화면에서 눈에 띄는가, 아니면 소스에만 있는가
2. **회원가입 폼** — 어떤 필드를 요구하는가, 필수와 선택이 구분되는가
3. **동의 UI** — 체크박스 구조를 정확히 본다
   - 필수와 선택이 분리되어 있는가
   - 기본 체크되어 있는가 (문제다)
   - "전체 동의" 하나로 마케팅까지 묶여 있는가 (문제다)
   - 동의 문구에 제15조 제2항 4가지가 다 나오는가 → `policy-checklist.md` 참조
4. **쿠키·자동수집 배너** — 있는가, 거부 수단을 주는가
5. **문의·뉴스레터 폼** — 로그인과 무관하게 개인정보를 받는 통로
6. **실제로 나가는 요청** — 네트워크 요청을 보고 어떤 외부 도메인으로 데이터가 가는지 확인. 코드에 없던 태그 매니저 스크립트가 여기서 잡히기도 한다

**방침 페이지 전문을 확보해 저장해 둔다.** Step 4의 대조 작업에서 원문이 필요하다.

## 모드 C — 설명으로 파악

코드도 URL도 없을 때. 질문으로 채운다. **한 번에 하나씩** 묻는다.

1. 사용자가 가입하나요? 가입할 때 뭘 입력받나요? (소셜 로그인이면 어디로?)
2. 로그인 말고 개인정보가 들어오는 통로가 있나요? (문의 폼, 이메일, 뉴스레터, 이벤트 응모)
3. 데이터는 어디에 저장되나요? (서비스 이름을 알면 리전도 함께 확인)
4. 붙여둔 외부 도구가 있나요? (분석, 결제, 알림, AI)
5. 탈퇴 기능이 있나요? 탈퇴하면 데이터는 어떻게 되나요?
6. 광고나 소식을 이메일·문자로 보내나요? 보낼 계획이 있나요?

모드 C로 만든 인벤토리는 **전부 "사용자 진술 기반"으로 표시한다.** 코드로 검증된 것과 같은 신뢰도로 다루지 않는다. 리포트에도 그렇게 명시한다.
